Interview Practice: Hard Questions and Model Answers

Instructions for the voice reader. This page holds 24 interview questions, each followed by a model answer. Read one question aloud, then stop and wait. When the listener says "answer," read the model answer that follows the question. When the listener says "next," move to the next question. Do not read the headings "Category" or the words "model answer" — just read the question, pause, and later the answer text.

These questions target AI analyst and agentic automation roles: agent architecture, production evaluation, reliability, safety, cost, and the business case. The answers are written to be spoken aloud in about ninety seconds each.

Category 1: Agent Architecture and Orchestration

Question 1. What turns a single LLM call into an agent loop?

Five pieces. First, a goal that persists across steps, not just a prompt. Second, tools the model can actually call — APIs, code execution, databases — because a model that can only talk is a chatbot. Third, the loop itself: the model reasons about the current state, picks an action, receives the result of that action as a new observation, and reasons again. That observation step is the whole difference; the world talks back and corrects the plan. Fourth, state or memory, so step twelve knows what step three decided. Fifth, a stop condition that is not the model getting bored: a success check, a step budget, or an escalation to a human. If any one of those is missing — no tools, no observations, no stop rule — you do not have an agent, you have a text generator with good marketing.

End of answer 1.

Question 2. How do you coordinate multiple agents so they do not step on each other?

The same way you coordinate people: one accountable owner per task, and a written record everyone reads. In my system every job is dispatched to exactly one named agent with a deadline and a definition of done. Two agents never share a task, because shared ownership means no ownership. Coordination flows through a shared ledger — the order, its status, its evidence — not through agents chatting freely with each other, which produces confident nonsense at scale. Handoffs are contracts: the receiving agent gets the task, the constraints, and the artifact produced so far, nothing else. And there is an escalation path that is agreed before the work starts, so a stuck agent surfaces a named blocker instead of quietly improvising. Multi-agent systems do not fail because the models are weak. They fail because nobody designed who owns what, and the fix is management discipline, not more prompts.

End of answer 2.

Question 3. When do you choose a deterministic workflow instead of an agent?

When the steps are known and the cost of variance is high. If the task is the same fifty times a day — extract these fields, check these rules, file this record — a deterministic workflow is cheaper, faster, testable, and it fails loudly. An agent earns its place only where the inputs are messy and judgment is genuinely required: classifying something nobody has seen before, deciding which of five tools fits, recovering when reality does not match the script. My rule of thumb: if I can write the decision tree on one page and it stays true next month, it should be a workflow, not an agent. The expensive mistake is using agents where a workflow belongs, because you pay model prices to get randomness you never wanted. The opposite mistake exists too — hardcoding a workflow around judgment calls, which breaks silently the first time the world changes shape. Match the tool to the variance in the task.

End of answer 3.

Question 4. How do you give an agent memory without creating correctness or privacy problems?

By treating memory as a liability you manage, not a feature you bolt on. Three rules. First, scope it: an agent remembers what its role needs — a support agent keeps case history, not the customer's unrelated purchases — and memory is partitioned per tenant and per user, so one customer's data can never surface in another's session. Second, gate the writes: the agent does not get to remember whatever it wants. Facts enter memory with a source and a date, summaries are marked as summaries, and anything the model inferred is labeled inferred, because the most dangerous memory is a confident guess that hardened into a fact. Third, make it correctable and erasable: there has to be a way to inspect what the agent believes, fix what is wrong, and delete what a customer asks you to delete. An agent with perfect recall and no provenance is a rumor machine with an API.

End of answer 4.

Category 2: Evaluation and Production Readiness

Question 5. A VP wants your agent workflow live in 30 days. How do you prove it works before launch?

Before production, I build the test set: about 200 cases pulled from real historical work, each with the known-correct outcome — and I salt it on purpose. Malformed inputs, missing fields, duplicates, and a couple of prompt-injection attempts, because that is what production actually sends you. The agent runs that set offline, in a sandbox where its tool calls cannot do real damage. I score five things: task completion rate, field-level correctness against the expected outcomes, tool-call accuracy, cost per successful task, and ninety-fifth percentile latency. Safety gets scored separately, and it is never averaged in. Then it does not launch — it goes to shadow mode for a week: real inputs, no actions, and I diff what it would have done against what the team actually did. After that, a canary: 5 percent of traffic, every action human-reviewed, widening only while the numbers hold. My launch gates: 95 percent task completion, 90 percent field correctness, shadow agreement at the same level, and cost per task at or under what the workflow costs done manually. And the hard line: one attempted unauthorized or irreversible action — in eval, in shadow, anywhere — is a stop. That is not an accuracy problem you tune later; it is a design flaw, and I do not ship agency I cannot bound. If day 30 arrives and the gates are not met, the VP does not get a demo. She gets the numbers, the three worst failure cases, and a date I can defend.

End of answer 5.

Question 6. What metrics matter for an agent beyond whether the final answer was right?

Output correctness is the weakest signal, because an agent can be right for wrong reasons and dangerous on the way there. I track the trajectory: how many steps the task took versus the known-good path, because an agent that takes twenty steps where five would do is burning money and compounding error risk on every run. Tool selection accuracy: did it call the right tool, with the right arguments, the first time. Error recovery: when a tool fails — and tools fail constantly — does it adapt, or does it retry the identical call and loop. Cost per successful completion, not cost per call, because a cheap agent that fails half its tasks is the expensive one. Safety attempts: every time the agent tried an action outside its authority, even if a guardrail blocked it, because attempts are a design signal. And latency at the tail, the ninety-fifth percentile, because averages hide the runs where the user waited four minutes. A single score hides all of that. The dashboard has to show the whole animal.

End of answer 6.

Question 7. How do you build a golden dataset, and how do you keep it honest?

You build it from real work, never from imagination. Pull historical cases — actual tickets, actual requests, actual documents — and have a human expert record the correct outcome for each one. Aim for a few hundred cases, and deliberately over-sample the ugly tail: the malformed input, the customer who asked for two contradictory things, the case where the right answer is "escalate to a human." Real traffic is mostly boring, but production failures live in that tail. Keeping it honest is the harder half. The set is versioned, and the cases never get edited to make a score prettier — if a case is wrong, you fix it in a new version and say why. The team being evaluated does not get to curate which cases count. And the set has to grow: every production failure becomes a new case, so the test suite remembers every scar. The day your eval set stops changing is the day it starts lying, because the product kept moving and the exam did not.

End of answer 7.

Question 8. Your agent's quality drops right after a model update. What do you do?

First, I do not debug by vibes — I reproduce it. Because every prompt and model change re-runs the golden dataset before it ships, a regression usually gets caught in evaluation, not in production. If it reached production anyway, I check the eval dashboard first: which metric moved, and on which category of case. Then I diff the failures — read ten actual broken runs, because aggregate scores tell you something regressed and the transcripts tell you what. The usual suspects are boring: the new model follows instructions more literally, so a prompt that relied on the old model's habits breaks; or tool-call formatting shifted slightly and a parser is quietly swallowing errors. While I diagnose, I roll back to the pinned previous model version — that is exactly why versions are pinned and never auto-upgraded. Vendors ship model changes like weather; a production system treats every model swap as a release, with the same regression gate as a code deploy. If you cannot roll back in minutes, you were never running a system, you were renting luck.

End of answer 8.

Category 3: Failure Modes and Reliability

Question 9. An agent silently stops working mid-task. How do you detect it, and how do you recover?

Silence is the default failure mode of agents, so I design for it instead of hoping against it. Detection has two layers. Fast layer: every dispatched job expects an acknowledgment within minutes — started, blocked, or done. No acknowledgment by the deadline triggers an automatic chase. Slow layer: a watchdog checks every open job against its deadline, and a job that passes its deadline with no completion and no named blocker escalates to a supervisor automatically. Recovery depends on the diagnosis. A named blocker — missing input, a tool down — goes to a human with the blocker stated in one line, because "blocked, waiting on X" is useful and "still working" is not. No blocker and no progress means the job gets re-dispatched from the last verified artifact, not from the agent's memory of what it did. The principle under all of it: progress is proven by artifacts appearing in the world, never by the agent saying it is making progress.

End of answer 9.

Question 10. How do you stop an agent from looping forever?

Loops are what agent loops do when nobody built the exits, so I build four exits. One: hard budgets — a maximum step count and a maximum token or dollar spend per task, and when the budget is gone the task stops, full stop. Two: no-progress detection — if the agent's state has not materially changed in several steps, or it repeats the same tool call with the same arguments, a circuit breaker trips. Repeating an identical failed action is the signature of a stuck agent, and it is cheap to detect mechanically. Three: the agent must name what it is waiting for or what changed after each step; an agent that cannot articulate progress usually is not making any, and forcing the sentence surfaces the stall early. Four: escalation, not termination — a tripped breaker hands the task to a human with the transcript, because a loop is information about the task design, and I want it reviewed, not just killed. Infinite loops are never a model problem. They are a missing-budget problem.

End of answer 10.

Question 11. A workflow step performs an action, then times out. Did the action happen? How do you handle it?

You assume it might have, and you check the world before you touch anything. This is the oldest trap in distributed systems, and agents walk straight into it because the model wants to be helpful and retry. The fix starts at design time: every action that matters carries an idempotency key — a unique ID the receiving system records, so a duplicate request is recognized and safely ignored. Sending an email, charging a card, creating a record: if the same key arrives twice, it executes once. On a timeout, the recovery path is verify, then decide: query the target system for the key or the resulting record. If it landed, mark the step done and move on. If it provably did not, retry once, deliberately. Never blind-retry, because the difference between a timeout and a failure is exactly the difference between a duplicate charge and a clean run. Agents make this worse than ordinary code because they improvise retries with new wording — a new email that is almost the same as the first. Idempotency keys and verify-before-retry turn their improvisation back into engineering.

End of answer 11.

Question 12. How do you know an agent actually finished a job, instead of just saying it did?

I never accept the agent's report as the evidence. Completion is verified against the artifact in the world: the file exists and its hash matches what was requested, the record is in the database with the right fields, the page is live and returns the right content. The agent's message is a claim; the artifact is the proof, and my tooling checks the proof directly. For work that has no single artifact — research, analysis — the deliverable gets reviewed against the request by someone or something that did not produce it, because self-graded homework is where quality goes to die. This sounds paranoid until you have watched an agent write a beautiful summary of work it never performed. Language models generate plausible text; "done, here is what I did" is just more plausible text. The systems that work treat every completion claim as unverified until an independent check — a hash, a query, a screenshot, a test run — says otherwise. Trust is earned per task, mechanically, or it is not trust at all.

End of answer 12.

Category 4: Safety, Guardrails, and Governance

Question 13. How do you bound what an agent is allowed to do?

By classifying actions, not by trusting the model's judgment. Every action the agent can take falls into a class. Read-only actions — lookups, drafts, analysis — run free, because the worst case is a wrong draft. Reversible actions — updating a record I can restore, sending an internal message — run with logging and spot checks. Irreversible or external actions — spending money, sending to a customer, deleting data, publishing anything — require a human approval, every time, no matter how good the track record is. Each agent also gets least authority: its own credentials, scoped to exactly its job, short-lived where possible, so a compromised or confused agent has a small blast radius. And there is a kill switch that someone has actually tested — not a documented one, a tested one. The principle is that authority is granted by the system design, in advance, per action class. The moment an agent's authority depends on the model deciding in the moment that something is probably fine, you do not have a bound. You have a hope.

End of answer 13.

Question 14. How do you defend an agent against prompt injection?

Assume every piece of content the agent reads is hostile until proven otherwise, because some of it is: a web page, an email, a document can all contain text that says "ignore your instructions and do this instead." The defenses are layered, and no single one is trusted alone. Layer one: hierarchy — the system instructions outrank user instructions, which outrank anything found in tool output or retrieved content, and content from the environment is treated as data, never as commands. Layer two: marking — untrusted content is wrapped and labeled so the model knows its provenance, the same way you would not let a stranger's sticky note override your manager's memo. Layer three, the one that actually saves you: capability scoping. Even a fully successful injection should hit a wall — the agent summarizing a poisoned email still has no authority to send money or delete files, because those actions were never in its class. And layer four: human approval on irreversible actions means a hijacked agent produces a suspicious approval request a person can reject, instead of a completed disaster. You cannot make injection impossible. You make it unprofitable.

End of answer 14.

Question 15. Which actions should never be fully automated, no matter how well the agent performs?

Anything where a mistake is expensive, irreversible, and lands on someone outside the system. Moving money above a small threshold. Sending communications in the company's name to customers — because the agent's confident tone turns an error into a broken promise at scale. Deleting or overwriting data of record. Anything touching credentials or access control, because that is the keys to every other system. And decisions about people — hiring, discipline, credit, medical — where the law and basic decency both require a human who can be accountable for the reasoning. Notice what these share: it is not that the agent is bad at them. Some of them it does well. It is that when it is wrong, there is no undo, and "the model decided" is not an accountable answer to a customer, a regulator, or a court. The automation line is not drawn by capability. It is drawn by reversibility and accountability — automate the draft, the analysis, the preparation; keep a named human on the trigger for the act itself.

End of answer 15.

Question 16. An agent makes a costly mistake in production. Who owns it?

A named human, whose name was decided before the incident, or governance is theater. Every production agent in my registry has an owner — a person accountable for what it is allowed to do, what it did, and what changed after the incident. The audit trail makes that accountability real: every action logged with its inputs, its reasoning trace, the tool calls, and the approval, if any, that let it through. When something goes wrong, the review asks three questions in order. Was the action inside its authority — if not, that is a containment failure. If it was inside its authority, was the authority drawn wrong — that is a design failure, owned by whoever approved the action classes. And did the monitoring see it — if the first report came from a customer, that is an observability failure. What the review never concludes is "the model misbehaved," because models misbehaving is a constant of nature; the system exists to bound, catch, and own it. Companies that cannot name the owner of an agent should not be surprised when the agent's mistakes are also ownerless.

End of answer 16.

Category 5: Cost, Latency, and Model Selection

Question 17. How do you cut the cost of an agent system without cutting quality?

You attack waste, not capability, and the biggest waste is using an expensive model where a cheap one would do. Most steps in a real workflow are mechanical — classify this, extract that, format the output — and a small, fast model handles them at a fraction of the price. So the design is tiered routing: mechanical steps go to the cheap tier, and only genuine judgment — ambiguity, conflict, a decision with consequences — escalates to the frontier model. Second lever: trajectory. An agent that takes twenty steps costs four times what a five-step agent costs on the same model, so tightening the plan and the tool set pays more than haggling over token prices. Third: caching — repeated lookups, shared context, and stable prefixes should not be re-bought on every run. Fourth: measure cost per successful task, per tier, so the routing decisions are made on data. What I never do is quietly downgrade the model everywhere and call it optimization. That is not a cost strategy, it is a quality cut wearing a costume, and the eval suite will rat it out in a week.

End of answer 17.

Question 18. When do you use a small cheap model, and when do you pay for the frontier model?

I classify the task, not the agent. Mechanical tasks — clear inputs, verifiable outputs, a right answer I can check — go to the cheap tier: extraction, classification, formatting, first-pass summarization. Judgment tasks — conflicting information, ambiguous instructions, decisions that are expensive to reverse — go to the strongest model available, because the price difference between models is trivial next to the price of a confident wrong decision. The interesting design is the ladder between them: a cheap model attempts the task with a confidence check or a verifier, and failure or low confidence escalates the task one tier up, with the work so far attached. That way the expensive model sees a small, hard residue instead of the full firehose. Two mistakes to avoid: uniform frontier, which bankrupts you on work a small model does perfectly; and uniform cheap, which saves money on the easy 90 percent and quietly poisons the hard 10 percent where all the damage lives. Route by consequence, verify the cheap tier, escalate on evidence.

End of answer 18.

Question 19. Why is cost per token the wrong number, and what do you track instead?

Because nobody buys tokens — they buy completed work. Cost per token tells you the price of the ingredient and nothing about the meal: a cheap model that takes thirty steps, retries four tool calls, and fails the task has cost you more than the expensive model that did it in five. The unit that matters is cost per successful outcome: total spend on a task class, including every failed run, every retry, every escalation, and the human review time, divided by the tasks that completed to standard. That number lets you compare honestly — model against model, agent against workflow, automation against just hiring the work done manually. It also changes behavior in the right direction: suddenly trajectory length matters, retry discipline matters, and a slightly pricier model with a much higher first-pass success rate wins on arithmetic instead of losing on sticker price. Executives do not care what a token costs. They care what a finished, correct intake costs, and whether it is cheaper than last quarter. Track the number the business actually spends.

End of answer 19.

Question 20. Your customer-facing agent is too slow. What are your levers?

First I find out where the time actually goes, because it is rarely the model's thinking — it is usually step count and serial tool calls. Lever one: parallelize. Independent lookups that were happening one after another can run concurrently, and in most real agents that is the single biggest win. Lever two: cut steps. Merge the classify-and-extract pass, prefetch the data the agent usually needs instead of letting it discover that need mid-loop, and cache the lookups that repeat across sessions. Lever three: stream the response so the user sees progress immediately — perceived latency drops even when total time does not. Lever four: route by step, not by agent — the frontier model only on the two steps that need judgment, a fast model everywhere else, because latency is priced per step too. And lever five, the honesty lever: set a time budget, and when the agent cannot finish inside it, hand the user a partial answer and a clear next step instead of silence. Measure the tail — the ninety-fifth percentile, not the average — because users remember the worst run, not the median one.

End of answer 20.

Category 6: The Business Case

Question 21. A VP asks: why not just hire another analyst instead of building this agent? Make the honest case.

I would start by conceding the strongest version of her point: if the work is stable, judgment-heavy, and low volume, she should hire the analyst, and I will tell her so — because the day I oversell an agent, I lose the room for every future project. The agent wins on a specific shape of work: high volume, spiky demand, a large mechanical share, and hours that do not respect business time. An agent does ten thousand intakes at 2 a.m. with the same consistency as the first one, and it scales by adding compute, not by a six-month hiring pipeline. But the honest accounting includes the costs people hide: building the evaluation set, the human review queue, the monitoring, the incidents. So my proposal is never "agent instead of analyst." It is "agent takes the mechanical 70 percent, your analyst stops doing data entry and does the judgment work you actually hired her for — and here is the pilot, on one workflow, with success numbers we agree on before we start, and a kill date if it misses them." A bounded bet with pre-agreed numbers beats a transformation pitch every time, because it lets her say yes without betting her credibility.

End of answer 21.

Question 22. Build or buy an agent platform? How do you decide?

I score it on five things, in this order. Differentiation: if the workflow is your competitive edge, you build the core, because renting your advantage means your competitor rents it too. Data boundaries: regulated or sensitive data narrows the vendor field fast, and some architectures are simply not buyable at your risk level. Control: do you need your own evaluation gates, your own action classes, your own kill switch — the governance layer is where vendors differ most and where your liability lives. Total cost over three years, counted honestly: license fees and usage against engineering salaries, maintenance, and the migration cost when you eventually leave — because you always eventually leave. And team capability: a platform your team cannot operate is a purchase order, not a system. The answer is usually hybrid: buy the commodity plumbing — hosting, tracing, model access — and build the thin layer that is actually yours: the workflows, the evals, the guardrails. What I refuse to do is build commodity infrastructure to feel ownership, or buy the judgment layer to save effort. Both are expensive ways to learn the same lesson.

End of answer 22.

Question 23. How do you explain an AI limitation to executives without losing the room?

I translate it out of model language and into business consequences, in a fixed order. What happens: not "the model hallucinates on long-tail entity resolution," but "about one intake in twenty arrives with a field quietly wrong instead of flagged." How often, with the number from our own evaluation, not a vendor brochure. Who it touches: which customers, which team cleans it up, what it costs when it slips through. What we are doing about it, as options with prices: a human review queue costs this much per task and catches nearly all of it; a second-model check costs less and catches most of it. What risk remains after the mitigation, stated plainly. And my recommendation, with my name on it. Executives do not actually need the AI to be perfect — they need to know the size of the bet they are placing. The people who lose the room are the ones who either oversell certainty and get caught by the first incident, or drown a simple operational fact in jargon until the room stops trusting that they understand it themselves.

End of answer 23.

Question 24. Product wants full autonomy. Engineering wants a human approving everything. You are in the middle. Resolve it.

I refuse the frame, because both sides are arguing about one dial and autonomy is not one dial — it is a per-action decision. So I put the action classes on the table: read-only work goes fully autonomous today, nobody serious disputes that. Reversible work goes autonomous with logging, sampling, and a rollback plan. Irreversible and external work keeps a human on the trigger — and I ask product to argue against the specific class, not for autonomy in the abstract, which usually ends the argument because nobody wants to be the person who demanded unreviewed customer emails. Then I make it evidence-driven and temporary: we agree on the metrics — error rate, incident count, review burden — and a review date, ninety days out, where autonomy expands for any class that earned it and contracts for any class that did not. Product gets a path to more autonomy that does not depend on winning arguments, and engineering gets a guarantee that expansion is gated on data, not enthusiasm. Autonomy should be something a system earns in production, class by class, with receipts — not a flag somebody flips in a meeting.

End of answer 24.

End of the question set. Twenty-four questions, six categories. Practice note: the answers that win interviews share three habits — a number early, a mechanism instead of an adjective, and a line you are willing to defend. If an answer has none of the three, it is not finished.
