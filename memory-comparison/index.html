1) Muse memory in one page

What it is. One assistant, one user. Memory "keeps lasting facts and preferences about the user for future conversations" and "notes can also be written in the background" [M-docs]. It is a file system on this VM, injected into every conversation — main chat and side chats share the same memory (Christopher was told this explicitly on 2026-10-12: a side chat's transcript starts fresh, but MEMORY.md, people files, and goals load into every chat) [M-log 2026-10-12].

The live layout [M-live, this run]: - ~/MEMORY.md — the curated long-term file, 22,610 bytes, headings: ## Facts, ## Preferences, ## Commitments, ## Built. Its own header states the rule: "durable facts, preferences, and commitments. Keep it tight: promote what lasts here, and leave raw day-to-day detail in your daily notes." - ~/memory/YYYY-MM-DD.md — dated daily logs, present continuously from 2026-09-09 through today (2026-10-16). Raw trail; MEMORY.md is the distilled version of it. - ~/memory/bank/ — runtime-managed synthesis files: experience.md, opinions.md, reflections.md, world.md. ~/memory/index/ exists and is runtime-managed (empty to a plain listing in this run). - ~/memory/people/ — 29 person pages plus INDEX.md, ordered by closeness; ~/memory/groups/ — 3 group pages plus INDEX.md [M-live]. - ~/memory/shopping/PROFILE.md — a domain profile the forget flow checks explicitly [M-forget]. - Side-chat memory: the memory tools document per-side-chat memory under ~/side-chats/<chat-id>/. On this VM in this run, ~/side-chats/ does not exist — so that store is documented but not observed here; no claim is made about its current contents.

The durable-vs-routine rule. Only what lasts belongs in MEMORY.md; routine detail stays in the daily log [M-live: MEMORY.md header]. Background upkeep enforces it: "Memory upkeep (hourly when there is new signal): new conversation is consolidated into MEMORY.md. Newer claims supersede older ones, and the dated notes under ~/memory/ keep the full trail" [M-improve]. The assistant also does its own bookkeeping during a session — upkeep "does not replace your own memory bookkeeping during a session: write down what's worth keeping when you learn it" [M-improve].

The other background jobs [M-improve]: Relationships (hourly — maintains the people/group pages), Dreaming (nightly — reviews recent conversations for what worked and what ruptured, writes dated reflections under ~/dreams/ and a synthesis of how to act for this user), Idea curation (daily), Studying (daily, overnight — goal briefings), Skill review (daily), and a bounded quiet-moment pass after a substantial conversation goes quiet. Demotions are visible in the trail: daily logs carry entries like "Demoted from MEMORY.md" with a run ID [M-log 2026-10-10, 2026-10-11, 2026-10-13] — promotion and demotion both happen, and both leave a record.

Retrieval. memory_search / memory_get search and read MEMORY.md, the daily notes, and side-chat memory, returning snippets with file-and-line citations; memory_explain traces where a claim came from and what replaced it [tool surface, as used in this workspace; M-forget references the same claim/citation machinery]. Memory search is explicitly separate from chat history search [M-docs].

Compaction — and its known failure mode. Long conversations are compacted into a model-written summary, not truncated. Live readout recorded 2026-10-13: context window 350,000 tokens, compaction trigger 272,000, retained tail ~20,000; what survives is controlled via the injected files (MEMORY.md / AGENTS.md / SOUL.md) and runtime state, and compaction is not configurable by Christopher or the assistant [M-log 2026-10-13]. Failure mode Christopher himself flagged on 2026-10-12: compaction drops in-progress plans. The mitigation in force is that the in-progress plan stays in the todo list until done — the todo list (a runtime database snapshot, keyed by conversation + agent [M-log 2026-10-13]) is what survives compaction. Standing rule recorded in ~/AGENTS.md (2026-10-12).

Secrets exclusion. "Keep raw credentials out of memory, files, environment variables, logs, and generated code" [M-privacy]. Credentials live in the Secure Vault / connector storage; the agent can confirm a saved login exists but can never see its values [M-privacy]. In practice: when Christopher pasted a GitHub token in chat on 2026-10-13, the token value was deliberately not recorded in memory or the daily log — only the fact, scope, and storage location were [M-log 2026-10-13; MEMORY.md Commitments].

Correction authority. The user corrects; the correction lands in MEMORY.md and every affected follow-up. Worked example, 2026-10-12: a MEMORY.md entry wrongly stated an AmericanMuscle purchase was completed. Christopher corrected it; the same day's log records the correction, and a later entry records "MEMORY.md correction applied" — the entry was rewritten to match reality (purchase NOT completed) [M-log 2026-10-12]. Same pattern for the deal watch (worse-CPU alerts killed and the job body + MEMORY.md updated together) [M-log 2026-10-13].

Forget. A dedicated, planned flow [M-forget]: forget.plan inventories everywhere the information could live (memory, reminders, created items, goals, scheduled work, derived copies), the user confirms the scope, then cleanup runs through each owning product action, claim IDs and MEMORY.md#L… / memory/<date>.md#L… locators are written to a pending file so the claims and everything derived from them are retracted and memory search is refreshed. "Forgotten" is only said when fresh verification finds no active copy and nothing that can write it back. Limits stated in the skill: outside services, shared/published items, logs and backups may remain and need separate approval; visible conversation text is not a cleanup target.

4) The three sharpest practical differences for Christopher

1. In Muse, being told is enough. In the fleet, being told is nothing until it's filed. You tell Muse a fact, a preference, or a correction in chat, and it is written down in-session, consolidated hourly, and re-injected into every future chat — the AmericanMuscle correction and the deal-watch scope change both propagated the same day you made them (2026-10-12/13). In Cadre, your 2026-10-13/14 experience was the opposite: instructions given in chat evaporated at the session boundary, which is why the overhaul had to transmit directives to Michael and record them in files (DECISIONS.md, AUTONOMY.md) to make them stick. Practical consequence: with the fleet, your unit of instruction is the file edit; with Muse, it's the sentence.

2. Muse's secrets gate is a wall; the fleet's is a to-do. Your credentials categorically never enter Muse's memory — when you pasted a GitHub token in chat, its value was recorded nowhere, by design [M-privacy]. In the fleet, tonight's scan confirmed plaintext keys sitting in openclaw.json (mode 600), and the fix — "Google key → SecretRef + rotate" — is recorded inside Michael's MEMORY.md as an open item, still unexecuted [A-audit F3/§4]. The fleet knows; knowing hasn't been a gate. If a secret matters, the only system here that structurally cannot leak it from memory is Muse, because it never holds it.

3. One memory vs seventeen — corrections and audits only travel as far as the file you touched. When Muse's memory is wrong, one correction fixes the single shared record every chat reads. In the fleet, a fact lives in up to 17 separate workspaces; there is no observed propagation, and tonight you watched the sharing gate fail in real time: your own audit's request for the memory/governance file matrix was declined by Michael, followed by Kif, and logged as a security finding — while on the Muse side, the duplicate-delivery divergence over Erin's lane (disabled here 2026-10-12, still running there) shows the two systems can hold contradictory "truth" about your own commitments with neither side noticing. Governing the fleet means governing files agent-by-agent; governing Muse means correcting one record.
